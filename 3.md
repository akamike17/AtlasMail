# 2. 🔴 HALLAZGO CRÍTICO — Restore no es realmente atómico

## Código afectado

`src/AtlasMail.Application/Services/BackupService.cs`

El flujo actual es:

```text
VALIDAR BACKUP
     ↓
VALIDAR TODO EL STORE
     ↓
WRITE-BACK DEL STORE
     ↓
APPLY SNAPSHOT DB
```

Esto evita que la DB apunte a un store parcialmente restaurado cuando el write-back falla.

Pero no resuelve el caso contrario:

```text
STORE RESTAURADO
     ↓
DB RESTORE FALLA
     ↓
STORE QUEDA MODIFICADO
DB puede quedar modificada/parcial
```

La implementación intenta resolver la DB mediante una transacción, pero `ApplySnapshotAsync()` ejecuta:

```sql
TRUNCATE TABLE ...
```

dentro de la transacción.

En MySQL `TRUNCATE TABLE` provoca implicit commit y no es rollbackable como una operación DML normal.

Por tanto:

```text
BeginTransaction
   ↓
TRUNCATE
   ↓
implicit commit
   ↓
INSERT / SaveChanges
   ↓
ERROR
   ↓
Rollback
```

**NO proporciona la atomicidad pretendida.**

## Evidencia insuficiente

Los tests de `BackupRestoreTests` utilizan `FakeAppDbContext` con EF InMemory.

Eso no demuestra la semántica real de MySQL.

Los integration tests prueban:

```text
backup → restore exitoso
```

pero no:

```text
backup
→ store publicado
→ fallo real durante restauración DB
→ rollback real
→ DB original intacta
→ store original intacto
```

## Veredicto

**🔴 ABIERTO**

La documentación no debe afirmar todavía:

> “restore atómico”

ni:

> “rollback verificable”

como propiedad completa del sistema MySQL.

# 3. 🔴 HALLAZGO CRÍTICO — Falta rollback del message store

Incluso eliminando el problema de `TRUNCATE`, el flujo actual publica primero el store:

```csharp
foreach (var (key, data) in storeData)
    await _store.SaveWithKeyAsync(key, data, ct);
```

y posteriormente modifica la DB.

Si `ApplySnapshotAsync()` falla:

```text
DB = estado anterior / parcialmente restaurado
STORE = estado del backup
```

No existe una operación equivalente a:

```text
rollback store
```

Por lo tanto la atomicidad DB + filesystem sigue sin existir.

## Solución requerida para cierre real

El restore necesita una estrategia de publicación transaccional fuera de la transacción SQL:

```text
BACKUP
  ↓
VALIDACIÓN COMPLETA
  ↓
STAGING DB
  ↓
STAGING STORE
  ↓
VALIDAR TODO
  ↓
PUBLICACIÓN CONTROLADA
  ↓
SWAP / COMMIT
  ↓
BORRADO DEL ESTADO ANTERIOR
```

O una estrategia equivalente que permita volver íntegramente al estado anterior.

# 4. 🔴 HALLAZGO — `AuthRateLimiter` no garantiza límite atómico bajo concurrencia

El diseño por IP es correcto:

```text
ConcurrentDictionary<IP, IpState>
                     ↓
                lock por IP
```

Esto es mucho mejor que un lock global.

Pero el flujo real es:

```text
IsAllowed(IP)
      ↓
verificación
      ↓
password hash
      ↓
RecordFailure(IP)
```

Dos o más conexiones pueden ejecutar simultáneamente:

```text
A → IsAllowed = true
B → IsAllowed = true
C → IsAllowed = true
...
```

antes de registrar los fallos.

Por tanto el límite no representa un contador estrictamente atómico de intentos concurrentes.

## Otro problema

Las entradas expiradas no tienen un recolector global.

Una IP puede quedar en:

```text
_states
```

después de su último intento y permanecer ahí indefinidamente si nunca vuelve a ser consultada.

El código sólo elimina la entrada cuando posteriormente se toca esa misma IP.

Por tanto:

```text
N IPs nuevas
   ↓
N entradas
   ↓
IP abandona el sistema
   ↓
entrada permanece
```

Esto contradice el objetivo de:

> expirar y eliminar entradas para impedir crecimiento ilimitado.

## Veredicto

**🔴 ABIERTO**

# 5. 🟠 HALLAZGO — `IsValidKey()` del filesystem no rechaza claves inválidas

`FileSystemMessageStore.Resolve()` primero normaliza:

```csharp
Regex.Replace(key, @"[^a-zA-Z0-9._-]", "_");
```

Por ejemplo:

```text
../../archivo
```

termina transformándose en algo similar a:

```text
.._.._archivo
```

Esto evita el escape del directorio.

Pero también significa que:

```text
StoreKey original != nombre realmente persistido
```

Eso es peligroso para el restore porque el `StoreKey` de la DB debe corresponder exactamente al archivo que se restaura.

La validación debería distinguir:

```text
clave válida
```

de:

```text
clave que puede normalizarse
```

y rechazar la segunda.

## Veredicto

**🟠 ABIERTO — integridad/correctitud**

No se observó un bypass directo de path traversal, pero sí una normalización que puede romper la correspondencia DB ↔ store.

# 6. 🟠 HALLAZGO — Test DATA infinito no verifica `421`

La implementación crea un `CancellationTokenSource` para `DataTimeout`.

Pero si el `ReadLineAsync()` termina por cancelación:

```csharp
catch (OperationCanceledException) { break; }
```

se abandona el loop directamente.

El `421` está en otra rama:

```text
entra una línea
→ comprueba DateTime.UtcNow - dataStarted
→ envía 421
```

Por lo tanto existen dos resultados posibles:

```text
DATA timeout
   ↓
cancelación del read
   ↓
cierre de socket
```

o:

```text
DATA timeout
   ↓
entra otra línea
   ↓
421
   ↓
cierre
```

El test actual solamente comprueba:

```text
closed == true
```

y tiempo < 4 segundos.

No comprueba obligatoriamente:

```text
421 4.4.2
```

## Veredicto

**🟠 ABIERTO — evidencia incompleta**

El timeout sí está probado como mecanismo de cierre, pero no el contrato exacto `421 + cierre`.
